"𝗔𝗰𝗰𝗲𝘀𝘀 𝘁𝗼 𝗳𝗲𝘁𝗰𝗵 𝗮𝘁 '𝗮𝗽𝗶.𝗲𝘅𝗮𝗺𝗽𝗹𝗲.𝗰𝗼𝗺' 𝗳𝗿𝗼𝗺 𝗼𝗿𝗶𝗴𝗶𝗻 '𝗳𝗿𝗼𝗻𝘁𝗲𝗻𝗱.𝗲𝘅𝗮𝗺𝗽𝗹𝗲.𝗰𝗼𝗺' 𝗵𝗮𝘀 𝗯𝗲𝗲𝗻 𝗯𝗹𝗼𝗰𝗸𝗲𝗱 𝗯𝘆 𝗖𝗢𝗥𝗦 𝗽𝗼𝗹𝗶𝗰𝘆." This is a common error. Right after deploying frontend and backend separately, everything seems fine… until the browser throws this dreaded message. 𝗖𝗢𝗥𝗦 𝗲𝗿𝗿𝗼𝗿. It may seem as if the browser is unnecessarily blocking progress. But here's what’s actually happening. 𝗖𝗢𝗥𝗦 (𝗖𝗿𝗼𝘀𝘀-𝗢𝗿𝗶𝗴𝗶𝗻 𝗥𝗲𝘀𝗼𝘂𝗿𝗰𝗲 𝗦𝗵𝗮𝗿𝗶𝗻𝗴) 𝗶𝘀 𝗮 𝗯𝗿𝗼𝘄𝘀𝗲𝗿 𝘀𝗲𝗰𝘂𝗿𝗶𝘁𝘆 𝗳𝗲𝗮𝘁𝘂𝗿𝗲. Its job is to prevent malicious sites from making unauthorized requests to servers. Why does it happen? When frontend and backend are hosted on different domains or ports, any API call across these is treated as a cross-origin request. The browser blocks it unless the server explicitly permits it. 𝗣𝗿𝗲𝗳𝗹𝗶𝗴𝗵𝘁 𝗥𝗲𝗾𝘂𝗲𝘀𝘁𝘀: Before sending certain types of requests (like those with custom headers or non-simple methods like PUT or DELETE), the browser sends a preflight request using the OPTIONS method to check if the actual request is safe. If the server doesn't respond with appropriate headers, the actual request is never sent. 𝗛𝗼𝘄 𝘁𝗼 𝗳𝗶𝘅 𝗶𝘁: The backend needs to send the correct CORS headers:  • 𝗔𝗰𝗰𝗲𝘀𝘀-𝗖𝗼𝗻𝘁𝗿𝗼𝗹-𝗔𝗹𝗹𝗼𝘄-𝗢𝗿𝗶𝗴𝗶𝗻: Specifies which origins are permitted  • 𝗔𝗰𝗰𝗲𝘀𝘀-𝗖𝗼𝗻𝘁𝗿𝗼𝗹-𝗔𝗹𝗹𝗼𝘄-𝗠𝗲𝘁𝗵𝗼𝗱𝘀: Lists allowed HTTP methods (GET, POST, etc.)  • 𝗔𝗰𝗰𝗲𝘀𝘀-𝗖𝗼𝗻𝘁𝗿𝗼𝗹-𝗔𝗹𝗹𝗼𝘄-𝗛𝗲𝗮𝗱𝗲𝗿𝘀: Lists allowed custom headers Frameworks like 𝗘𝘅𝗽𝗿𝗲𝘀𝘀, 𝗗𝗷𝗮𝗻𝗴𝗼, and 𝗦𝗽𝗿𝗶𝗻𝗴 𝗕𝗼𝗼𝘁 provide easy ways to handle this:  • In Express (Node.js), use the cors middleware  • In Django, use the django-cors-headers package  • In Spring Boot, configure CORS mappings via annotations or config classes 𝗕𝗲𝘀𝘁 𝗽𝗿𝗮𝗰𝘁𝗶𝗰𝗲𝘀:  • In production, always be specific with allowed origins. Avoid * unless building a public API.  • Test both simple and preflighted requests.  • Understand request types. The method and headers influence whether a preflight is triggered. 𝗖𝗢𝗥𝗦 𝗶𝘀 𝗻𝗼𝘁 𝗮 𝗯𝘂𝗴. It's a 𝘀𝗲𝗰𝘂𝗿𝗶𝘁𝘆 𝗽𝗿𝗼𝘁𝗼𝗰𝗼𝗹 that exists for good reason. It protects applications and users from cross-site attacks and misuse.
