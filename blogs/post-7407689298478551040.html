𝗪𝗵𝗮𝘁 𝗵𝗮𝗽𝗽𝗲𝗻𝘀 𝗶𝗳 𝘁𝘄𝗼 𝗺𝗶𝗰𝗿𝗼𝘀𝗲𝗿𝘃𝗶𝗰𝗲𝘀 𝘁𝗿𝘆 𝘁𝗼 𝗺𝗼𝗱𝗶𝗳𝘆 𝘁𝗵𝗲 𝘀𝗮𝗺𝗲 𝗱𝗮𝘁𝗮𝗯𝗮𝘀𝗲 𝗿𝗲𝗰𝗼𝗿𝗱 𝗮𝘁 𝘁𝗵𝗲 𝘀𝗮𝗺𝗲 𝘁𝗶𝗺𝗲? A friend recently asked me this question, and after exploring it, here are the key findings. In this post, I will try to cover it in brief so that everyone can understand. When two independent services attempt to write to the same data, the system can run into issues like lost updates, version conflicts, and inconsistent state. To handle this, backend systems generally follow a few well-established approaches: 1. Pessimistic Locking The database locks the record during a transaction to prevent parallel writes. Reliable, but may affect performance. 2. Optimistic Locking Each record has a version or timestamp, and updates succeed only if versions match. This scales well and is widely used. 3. Distributed Locking Using tools like Redis or ZooKeeper when multiple services across nodes need exclusive access. 4. Event or Saga-Based Designs Instead of writing directly to the same table, services communicate through events and avoid touching the same record. Most importantly: Each microservice should ideally own its data. If two services need interaction on the same business entity, sharing information through events or APIs is safer than competing writes to a shared table.
