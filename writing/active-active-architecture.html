Distributed Database Architectures | Active-Active Architecture Application

Originally published Jul 14, 2025

  • Distributed Systems
  • Databases
An on-site adaptation of Ashmita’s earlier article, not a verbatim republication.

Serving traffic from more than one region can reduce latency and let some parts of an application keep running through a regional failure. The difficult question is what each region is allowed to write when it cannot reach the others.

Separate coordination, replication, and partitioning

Two-phase commit coordinates whether participants commit a shared transaction; it can add cross-region latency and may block in certain failures. A multi-primary design can accept writes at several locations, but concurrent changes need a clear coordination or conflict strategy. Sharding splits data ownership by a key, so different regions or nodes can handle different records. Shards can also be replicated: partitioning alone does not provide redundancy.

Give each operation an appropriate guarantee

In a shopping application, an inventory reservation may need stronger coordination than a product-description update, because selling the same last unit twice has a meaningful cost. Test the design by imagining a region isolated during a sale. Decide which writes can continue, which must wait, and how the system will recover once connectivity returns.
