Bloom Filters: How Databases Avoid Millions of Unnecessary Disk Reads

Originally published Aug 9, 2026

  • Databases
  • System Design
An on-site adaptation of Ashmita’s earlier article, not a verbatim republication.

A storage engine looking up a key may have several files to inspect, even when none contains the key. A Bloom filter gives it a cheap way to rule out files before reading them.

What the filter knows

Hash each inserted key to several positions in a bit array and turn those bits on. At lookup, repeat the hashes. A zero bit rules out the key, provided the filter covers the data being checked and its bits have been maintained correctly. If every bit is set, the key still might be absent: unrelated keys can set the same combination. That is why the database must check the underlying file after a positive result.

Where it pays off

A filter per sorted table file lets an engine such as Cassandra skip files that cannot contain the requested key. The benefit is greatest when negative lookups are common and a disk read costs much more than a membership check. As more keys fill the array, false positives rise. Size the filter for its expected workload, and don't clear individual bits to delete a key: another key may share them. If deletion is essential, consider a counting filter or rebuild the filter with the file.
