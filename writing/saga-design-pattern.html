SAGA Design Pattern in Microservice Architecture

Originally published Feb 23, 2026

  • Distributed Systems
  • Microservices
An on-site adaptation of Ashmita’s earlier article, not a verbatim republication.

An order can touch inventory, payments, and shipping, each backed by a separate service and database. A saga turns that cross-service transaction into local steps, with an explicit response when a later step fails.

Compensate for work already done

An order service can create a pending order, reserve a unit of inventory, and attempt the payment. If payment is declined, it can release the reservation and mark the order as failed. These actions do not rewind a shared database transaction. They are new operations with business meaning, and those operations can fail as well. Record the state of each step, make retries safe, and define what happens when a compensating action cannot complete automatically.

Choose how the steps are coordinated

In a choreographed saga, services react to one another's events. That can be straightforward with few steps, but the full flow becomes harder to follow as dependencies grow. In an orchestrated saga, one workflow component directs the steps and records progress, making execution easier to inspect while introducing a component that needs reliable state. With either design, expect intermediate states and decide what users should see while a workflow is pending.
