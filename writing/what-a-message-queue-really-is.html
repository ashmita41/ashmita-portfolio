What a Message Queue Really Is

Originally published Feb 7, 2026

  • System Design
  • Distributed Systems
  • Messaging
An on-site adaptation of Ashmita’s earlier article, not a verbatim republication.

A queue looks simple when both sides are healthy: a producer puts a message in, a consumer takes it out. The useful design decisions show up when one side crashes, stalls, or responds late.

Receiving is not the same as completing

In a basic in-memory queue, taking an item removes it. If a worker crashes just before it finishes, the job is lost. A more reliable design tracks an item as in flight and removes it only after acknowledgment. If the worker does not acknowledge it by a deadline, the queue can make it available for another attempt. This introduces the opposite risk: a worker might finish the action but fail before sending the acknowledgment.

Plan for repeats, overload, and stuck jobs

When a delivery can repeat, make the consumer's action safe to repeat too. A durable job identifier can help a worker recognize an event it already processed. Limit retries and send repeated failures somewhere they can be inspected, rather than letting one bad message loop forever. And if producers outrun consumers, use prefetch limits, bounded concurrency, or admission control. A queue can absorb a burst; it cannot resolve a permanent gap between arrival rate and processing capacity.
