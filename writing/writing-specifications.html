Stop Vibe Coding. Start Writing Specifications.

Originally published Jul 13, 2026

  • AI
  • Engineering Practices
An on-site adaptation of Ashmita’s earlier article, not a verbatim republication.

A quick prompt can be enough to find out whether an idea is worth building. Once the code has to fit an existing system, the challenge changes: the assistant needs to know which decisions are already made, which behavior must remain, and what success looks like.

Write down the decisions before generating code

Start with the user outcome, then define inputs, outputs, permissions, failure paths, and explicit non-goals. For a pagination task, for example, record the sort order, the tie-breaker, and what happens when the first page is empty. These details give the assistant something concrete to implement and the reviewer something concrete to check. Use examples and expected results wherever a sentence could reasonably be read two ways.

Keep the spec with the implementation

Review the proposed approach before asking for the patch. Then use the agreed examples as acceptance tests. When you change a requirement, update the document and tests along with the code so the next person or tool can tell which behavior is intentional. The point is not a long document. It is a short, durable record of the decisions you would otherwise have to explain again.
